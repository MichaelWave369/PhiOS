# Macro Runtime v0.12 — Operator Log + Ghost-Walk Interaction Guard\n\n## Status\n\nVersioned editable operator annotations plus guarded window-relative pixel anchors.\n\nv0.12 incorporates practical field feedback from an existing macro-automation user:\n\n- long-run loops can drift;\n- editable logs are useful for correcting human context;\n- random popups, focus changes, or mouse movement can derail blind replay;\n- observed user actions can be useful as a ghost walk for building automation.\n\n## Core boundary\n\n~~~\nEDITABLE NOTE != EDITABLE REALITY\nPIXEL ANCHOR != AUTHORITY\nCLEAR GUARD != AUTHORIZATION\nGHOST WALK != BLIND REPLAY\nWINDOW-RELATIVE COORDINATE != FIXED DESKTOP COORDINATE\nOPERATOR INPUT != AUTOMATION NOISE\nUNKNOWN UI STATE -> HOLD\n~~~\n\n## Versioned Operator Log\n\nThe immutable Reality Ledger remains unchanged.\n\nHuman notes are stored separately in:\n\n~~~\noperator-log-revisions.jsonl\n~~~\n\nAn OperatorLogRevision binds:\n\n- note ID;\n- contiguous revision number;\n- immutable target SHA-256;\n- author ID;\n- body;\n- sorted tags;\n- ACTIVE or RETRACTED status;\n- timestamp;\n- previous revision SHA-256;\n- zero authority flags.\n\nEditing a note means appending a new revision.\n\nThe original revision remains present and hash-verifiable.\n\nStale edits fail closed through expected-current-revision checking.\n\nThis allows a human to correct context without rewriting execution evidence.\n\nExample:\n\n~~~\nrevision 1: Popup interrupted cycle 46. It was Chrome.\nrevision 2: Correction: popup was NVIDIA.\n~~~\n\nBoth revisions remain linked to the same immutable execution/state hash.\n\n## Ghost-walk pixel anchor\n\nA user-observed click can be converted into a PixelAnchor.\n\nThe anchor stores both:\n\n- original absolute desktop pixels;\n- normalized position inside the source window, in parts-per-million.\n\nExample:\n\n~~~\nsource window: left=100 top=50 width=800 height=600\nobserved click: x=500 y=350\n\nrelative position:\nx = 50% across the window\ny = 50% down the window\n~~~\n\nIf the same verified app/window later moves or resizes, the anchor resolves against\nthe new window geometry instead of blindly replaying desktop (500,350).\n\nThis is the first concrete version of Jeffrey's suggested coordinate mapping.\n\n## Window identity\n\nA WindowFrame binds:\n\n- process identity;\n- hashed window title identity;\n- desktop geometry;\n- display scaling;\n- foreground state;\n- capture timestamp;\n- zero authority flags.\n\nThe interaction guard compares the current frame with the anchor contract before\nproducing a usable coordinate.\n\n## Interference guard\n\nInteractionGuard assesses:\n\n- process mismatch;\n- window-title mismatch;\n- lost foreground focus;\n- unexpected overlay / popup;\n- operator keyboard/mouse input;\n- pointer movement since the expected anchor state;\n- resolved coordinate bounds.\n\nAny interference produces:\n\n~~~\ndecision = HOLD\nresolved_x_px = null\nresolved_y_px = null\n~~~\n\nOnly a clean matching frame produces CLEAR with a resolved coordinate.\n\nCLEAR means only:\n\n> the interaction frame and interference checks passed.\n\nIt does not grant action or execution authority.\n\n## Operator takeover semantics\n\nHuman input is not treated as noise to overpower.\n\nIf mouse/keyboard activity is detected during a guarded interaction window, PhiOS\nshould interpret it as possible operator takeover and HOLD.\n\nThe automation should not wrestle the user for the cursor.\n\n## Persistence\n\nReality Ledger adds:\n\n~~~\ninteraction-guard-receipts.jsonl\n~~~\n\nEach receipt binds:\n\n- anchor hash;\n- current frame hash;\n- CLEAR / HOLD decision;\n- exact reasons;\n- resolved coordinates when CLEAR;\n- observation timestamp;\n- zero authority flags.\n\n## v0.12 acceptance gates\n\n### OPLOG-001 — create and retrieve\n\nA note linked to an immutable target hash can be created and read back.\n\n### OPLOG-002 — editable by revision\n\nAn edit appends revision N+1 without modifying revision N.\n\n### OPLOG-003 — stale edit rejection\n\nAn edit based on an old current-revision hash is rejected.\n\n### OPLOG-004 — retraction by revision\n\nRetraction appends a RETRACTED revision rather than deleting history.\n\n### OPLOG-005 — tamper detection\n\nModified persisted note content fails hash verification.\n\n### GUARD-001 — window-relative remapping\n\nA ghost-walk click remains resolvable when the same app/window moves or resizes.\n\n### GUARD-002 — interference HOLD\n\nProcess mismatch, title mismatch, focus loss, overlay, operator input, or pointer\nmovement returns HOLD with no resolved coordinate.\n\n### GUARD-003 — source bounds\n\nA click outside the observed source window cannot become an anchor.\n\n### GUARD-004 — guard evidence\n\nInteraction guard decisions are persisted as immutable receipts.\n\n### GUARD-005 — zero authority\n\nPixel anchors and guard receipts carry no operational, action, or execution\nauthority.\n\n## What this means for recorded loops\n\nPhiOS should not treat a recorded loop as a tape of desktop coordinates.\n\nA better model is:\n\n~~~\nobserve user action\n→ identify app/window\n→ create normalized pixel anchor\n→ retain optional semantic hint\n→ before replay, revalidate current frame\n→ detect operator/popup interference\n→ resolve current coordinate\n→ downstream authority check\n→ adapter action\n→ verify post-action state\n~~~\n\nThis preserves the intuitive ghost-walk experience while making the replay less\nfragile than traditional mouse recorders.\n\n## Deliberate non-goals\n\nv0.12 does not yet:\n\n- capture real OS mouse/keyboard events;\n- inject mouse/keyboard input;\n- inspect screenshots;\n- detect overlays directly;\n- read accessibility trees;\n- store typed secrets;\n- execute a CLEAR interaction;\n- convert full demonstrations into MacroDefinition automatically.\n\nThese contracts are the guard rails those adapters must obey later.\n\n## Next rung\n\nv0.13 should add a real Demonstration / Ghost-Walk Recorder contract.\n\nIt should capture user actions as observations and propose MacroDefinition steps\nusing a priority order like:\n\n~~~\nsemantic selector when available\n→ window-relative pixel anchor as fallback\n→ fixed desktop coordinate only as last-resort evidence\n~~~\n\nThe recorder may propose automation.\n\nIt still must not grant execution authority.
