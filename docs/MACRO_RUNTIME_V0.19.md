# Macro Runtime v0.19 — Post-Action State Verification\n\n## Status\n\nv0.19 closes the gap between proving that PhiOS injected one governed desktop\ninteraction and proving that a declared observable application state appeared\nafterward.\n\nIt adds bounded synchronous post-action observation and binds the expected state\ninto the exact macro operation payload governed by the existing PlanActionBinding\nand ActionLease path.\n\n## Core boundary\n\n~~~\nCLICK SUCCEEDED != APPLICATION INTENT SUCCEEDED\nOBSERVED AFTER ACTION != CAUSED BY ACTION\nPOSTCONDITION != AUTHORITY\nVERIFIED OBSERVATION != CAUSAL PROOF\nNOT VERIFIED != SAFE TO CONTINUE\nINDETERMINATE != FAILURE PROOF\n~~~\n\n## Compatibility\n\nLegacy v0.18 Ghost-Walk click payloads remain valid.\n\nIf a payload has no post_action_expectation, the executor retains v0.18 behavior.\n\nIf a payload includes post_action_expectation, v0.19 requires a configured\nPostActionVerifier and the expectation becomes part of the exact operation\npayload hash.\n\nThe desktop capability version advances to:\n\n~~~\ndesktop.interaction.click 0.19.0\n~~~\n\nExisting bindings and ActionLeases created against v0.18 therefore do not\nsilently authorize the changed runtime contract.\n\n## Expectation contract\n\nPostActionExpectation supports four initial observable state predicates:\n\n~~~\nWINDOW_TITLE_EQUALS\nWINDOW_TITLE_CHANGED\nSEMANTIC_PRESENT\nSEMANTIC_ABSENT\n~~~\n\nEvery expectation binds:\n\n- expected process ID;\n- source window-title SHA-256;\n- optional expected window-title SHA-256;\n- optional v0.16 SemanticTarget;\n- max observation count;\n- observation interval;\n- zero authority flags.\n\nEach expectation has a canonical SHA-256.\n\n## Exact pre-action binding\n\nBefore injection, the executor requires:\n\n~~~\nexpectation.expected_process_id == click.process_id\nexpectation.source_window_title_sha256 == click.window_title_sha256\n~~~\n\nAn expectation cannot be attached to an unrelated process or source window.\n\nBecause the expectation object remains inside the macro operation payload, the\nexisting payload hash, PlanActionBinding, EffectIntent, and ActionLease bind the\nexact click plus its exact expected postcondition.\n\n## Bounded observation\n\nPostActionVerifier performs a bounded synchronous observation loop.\n\nCurrent limits:\n\n~~~\n1 <= max_observations <= 10\n0 <= interval_ms <= 2000\n~~~\n\nThe verifier never creates a background worker and never continues checking\nafter the governed operation returns.\n\nEach observation records:\n\n- observation index;\n- MATCH / NO_MATCH / INDETERMINATE;\n- exact reason;\n- timestamp;\n- current WindowFrame hash when available;\n- semantic replay receipt hash when applicable.\n\n## Window expectations\n\n### WINDOW_TITLE_EQUALS\n\nThe foreground process must remain the expected process.\n\nThe current window-title hash must equal the declared expected hash.\n\n### WINDOW_TITLE_CHANGED\n\nThe foreground process must remain the expected process.\n\nThe current window-title hash must differ from the source title hash.\n\nA title change is an observable transition only. It is not proof that the\nclick caused that transition.\n\n## Semantic expectations\n\n### SEMANTIC_PRESENT\n\nThe verifier uses the merged v0.17 SemanticReplayRevalidator against the\ndeclared expected process/window.\n\nExactly one safe target resolving CLEAR means MATCH.\n\nTARGET_MISSING means NO_MATCH.\n\nAmbiguity, backend failure, scope drift, unknown state, or other HOLD reasons\nremain INDETERMINATE.\n\n### SEMANTIC_ABSENT\n\nOnly v0.17 TARGET_MISSING counts as MATCH.\n\nA still-present CLEAR target is NO_MATCH.\n\nAmbiguity or observation failure cannot be reinterpreted as absence.\n\n## Final verification decision\n\nIf any bounded observation MATCHes:\n\n~~~\nVERIFIED\n~~~\n\nIf no observation matches and every observation is a valid NO_MATCH:\n\n~~~\nNOT_VERIFIED\n~~~\n\nIf no observation matches and any observation is uncertain:\n\n~~~\nINDETERMINATE\n~~~\n\nUnknown evidence therefore dominates false certainty.\n\n## Separation from the click receipt\n\nv0.18 DesktopInteractionReceipt remains the evidence for the actual injected\ninput sequence.\n\nv0.19 adds a separate:\n\n~~~\nPostActionVerificationReceipt\n~~~\n\nThis separation allows the ledger to represent:\n\n~~~\ndesktop click: SUCCEEDED\npostcondition: NOT_VERIFIED\noverall macro operation: OUTCOME_UNKNOWN\n~~~\n\nwithout rewriting the history of the input event.\n\n## Macro execution behavior\n\nWhen a postcondition is declared:\n\n~~~\n3/3 SendInput events inserted\n-> DesktopInteractionReceipt(SUCCEEDED)\n-> bounded PostActionVerifier\n~~~\n\nIf verification is VERIFIED:\n\n~~~\nSpine execution SUCCEEDED\n-> DoDispatchResult SUCCEEDED\n-> MacroRunner continues\n~~~\n\nIf verification is NOT_VERIFIED or INDETERMINATE:\n\n~~~\nOutcomeUnknownError\n-> Spine execution outcome_unknown\n-> reconciliation required\n-> macro operation resolution HELD\n-> MacroRunner stops\n~~~\n\nThe already-consumed ActionLease is not restored.\n\n## Persistent evidence\n\nReality Ledger adds:\n\n~~~\npost-action-verification-receipts.jsonl\n~~~\n\nEach PostActionVerificationReceipt binds:\n\n- DesktopInteractionReceipt SHA-256;\n- exact full operation payload SHA-256;\n- expectation SHA-256;\n- VERIFIED / NOT_VERIFIED / INDETERMINATE;\n- final reason;\n- complete bounded observation sequence;\n- verification timestamp;\n- causation_proven = false;\n- zero authority flags.\n\n## Causality firewall\n\nv0.19 explicitly fixes:\n\n~~~\ncausation_proven = false\n~~~\n\neven for VERIFIED transitions.\n\nThe receipt supports the statement:\n\n~~~\nthe declared state was observed after the governed interaction\n~~~\n\nnot:\n\n~~~\nthe interaction was proven to be the sole cause of the state\n~~~\n\nStronger causal attribution would require additional experimental or\napplication-specific evidence.\n\n## v0.19 acceptance gates\n\n### POST-001 — delayed title transition\n\nA title transition that appears within the bounded observation budget verifies.\n\n### POST-002 — expected title absent\n\nA title expectation that never appears returns NOT_VERIFIED.\n\n### POST-003 — semantic present\n\nA unique v0.17 CLEAR semantic target verifies SEMANTIC_PRESENT.\n\n### POST-004 — semantic absent\n\nOnly explicit TARGET_MISSING verifies SEMANTIC_ABSENT.\n\n### POST-005 — semantic ambiguity\n\nMultiple matching semantic targets return INDETERMINATE.\n\n### POST-006 — process drift\n\nUnexpected foreground process state returns INDETERMINATE before semantic lookup.\n\n### POST-007 — hash-bound expectation\n\nExpectation serialization round-trips with canonical SHA-256 validation.\n\n### DESKTOP-012 — verified postcondition\n\nA successful click plus VERIFIED expectation returns a normal artifact.\n\n### DESKTOP-013 — unverified postcondition\n\nA successful click plus NOT_VERIFIED expectation raises OUTCOME_UNKNOWN while\npreserving the successful DesktopInteractionReceipt.\n\n### DESKTOP-014 — full macro stop\n\nA leased governed click whose postcondition is not verified propagates through\nthe Spine as outcome_unknown and stops the MacroRunner at HELD.\n\n## Deliberate non-goals\n\nv0.19 does not yet:\n\n- infer postconditions automatically from a demonstration;\n- claim causality;\n- use OCR/text-content predicates;\n- compare screenshots perceptually;\n- verify arbitrary application business data;\n- retry the desktop interaction after an unverified result;\n- issue new authority from verification evidence.\n\n## Next rung\n\nv0.20 should teach Ghost-Walk to infer candidate transition expectations from\ndemonstrated before/after UI states.\n\nThat layer should remain zero-authority and produce editable candidate\npostconditions for operator review rather than silently deciding what the human\nintended.
