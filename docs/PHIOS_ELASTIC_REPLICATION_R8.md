# PhiOS Elastic Runtime R8: join PhiStream staging and replicated prefill evidence

**Status: research-alpha, fully offline and advisory.** This PR does not run a pretrained model, alter a GPU/driver/kernel, promote a scheduler, install PhiStream, or execute a resource residency policy.

## Why this is different from R7

R7 reviews the narrow [PhiStream weight-stage audit](https://github.com/MichaelWave369/PhiStream/blob/main/docs/WEIGHT_STAGE_AUDIT.md) of four operator-supplied SmolLM2-135M-Instruct decoder receipts. It checks stage byte/operation counters and time fractions, **not** that reducing staged bytes makes model inference faster.

PhiStream separately documents a [paired real prefill benchmark](https://github.com/MichaelWave369/PhiStream/blob/main/docs/PAIRED_REAL_PREFILL_AB.md) and [cross-day replication review](https://github.com/MichaelWave369/PhiStream/blob/main/docs/REPLICATION_REVIEW.md). The latter re-checks original and replicated A/B trials against local checkpoint/reference evidence. Their comparison is **SINGLE vs BATCHED prompt prefill**, not a measurement of PhiOS's R1 bubble eviction and not a cold-file or PCIe bandwidth benchmark.

R8 combines these *two published audit formats* into one sanitized PhiOS review only when the source checkpoint fingerprints and the frozen `spread_24` reference SHA match. It verifies internal summary arithmetic, declarations, matched greedy-ID/probe counts and frozen trial design metadata before presenting the two observations alongside each other. It does **not** rehash the original model or source traces, authenticate original experiments, or prove an optimization.

## Explicit input contract

- Stage audit: PhiStream `PHISTREAM_WEIGHT_STAGE_AUDIT_V1` (the same input as R7).
- Replication audit: PhiStream `PHISTREAM_REPLICATION_REVIEW_V1` generated by `scripts.replication_review`.
- Both files must be explicitly selected, local, bounded to 128 KiB each, regular, non-symlink JSON without duplicate fields or nonfinite constants.
- Requires the same checkpoint fingerprint and `spread_24` reference digest across both source audits, as well as matching expected no-execution/no-proven-speedup flags.
- Recognizes the original 4-pair case, replicated 8-pair case, original seed 369, replicated seed 70421, 32 greedy IDs per recorded execution, ≥8 sampled logit coordinates per step, and the fixed four-cohort 20-pair / 48-execution design. Note that these **count checks do not individually re-verify every generated ID**.
- Rechecks each cohort's predeclared descriptive threshold (≥5% median paired wall-time reduction; candidate faster in ≥75% of pairs) and the claimed replication-versus-original gain difference.
- Rejects inconsistent or unearned claims, unknown fields and unsupported source revisions. A replication that does not meet the threshold stays `INCONCLUSIVE`, not a positive result.

## Command

From a PhiOS Python 3.11+ environment with the two **already-existing** local PhiStream audit files:

```bash
python -m phios.elastic_replication_r8 \
  --stage-audit "/path/to/weight-stage-audit.json" \
  --replication-review "/path/to/replication-review-seed70421.json"
```

In Windows PowerShell, use one line or a PowerShell backtick for line continuation:

```powershell
py -m phios.elastic_replication_r8 --stage-audit "D:\PhiStream\Experiments\weight-stage-audit.json" --replication-review "D:\PhiStream\Experiments\replication-review-seed70421.json"
```

Both paths above are examples, not automatically present files. The command does not discover or download checkpoints and never creates results on disk unless stdout is explicitly redirected.

**Exit status:** 0 means structurally consistent `REVIEW_REQUIRED`; 3 means a structurally consistent but `INCONCLUSIVE` replication; 2 means invalid, missing, unsupported or mismatched data (`UNAVAILABLE`). Zero does **not** grant action authority.

## Output and interpretation

The PhiOS `phios.elastic.phistream-replication-join.v1` output includes only:

- Original R7 staging share, stage payload per single-token step and four-case count
- Original and replicated `spread_24` medians for decoder and time-to-first-logits **relative gain**, paired win counts, provenance-limited parity counters, and weight-staging-byte differences
- Combined 20-pair aggregate and 48-execution parity **counts declared by the source audit**, plus the percent-point difference between the original and replication median gains
- SHA-256 hashes of the **submitted audit objects** and the deterministic PhiOS receipt

It does not export checkpoint fingerprints, prompt tokens, logit samples, pathnames, weights, or model configuration internals. Hashes protect against accidental mismatch, not fabrication; these source audits are **user-supplied**.

The following flags always remain false:

```text
original_checkpoint_bytes_rehashed
real_model_executed_here
external_reference_authenticated
independent_replication_attested
statistical_significance_established
general_speedup_proven
automatic_scheduler_promotion
action_authority
execution_authority
hardware_control
```

**Do not combine the observed ~82% staging share with a measured prefill gain to calculate an additional projected speedup.** The stage fraction covers one-shot single-token loading, and the prefill experiment replaces a different execution path. The metrics are confounded and do not add or multiply.

## Test

```bash
python -m pytest -q tests/test_elastic_replication_r8.py
```

`experiments/elastic/r8_illustrative_joint.json` contains **invented, synthetic test-only reports** with compatible fields and consistent arithmetic. Their apparent 20/20 paired wins, RTX device label and timing ratios are fixtures, not fresh measurements on any user machine. CI must never download the model or run the actual GPU benchmark.

## Next gate

For an actual future PhiOS/PhiStream resource-management experiment, first gather **operator-authorized, held-out model tests** with exact output parity, explicit VRAM reservation, staging and first-token timing, power/thermal conditions, and matched controls. Then evaluate a **reversible, separately authorized** caching policy against the untouched SINGLE baseline. The review here does not promote R1 resource plans or alter PhiKernel/TIEKAT.
