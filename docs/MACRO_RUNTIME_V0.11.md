# Macro Runtime v0.11 — Schedule Worker Ownership + Anti-Drift Cycles\n\n## Status\n\nSingle-host schedule-worker ownership and deterministic one-tick execution over\nthe merged v0.10 persistent ScheduleService.\n\nv0.11 introduces a live worker ownership contract, but it still does not give\nthe worker authority over macro operations.\n\n## Core boundary\n\n~~~\nWORKER OWNERSHIP != MACRO AUTHORITY\nPOLL OWNERSHIP != OPERATION AUTHORITY\nLEASE != CAPABILITY GRANT\nTICK != EFFECT EXECUTION\nCYCLE MEMORY != TRUST\nOS LOCK != REALITY PROOF\n~~~\n\nThe worker may own one schedule-service polling lane.\n\nAny macro started by that polling still reaches the same downstream\nWAITING_OPERATION / ActionLease / Spine boundaries.\n\n## Live ownership\n\nEach service is fenced by a live OS file lock stored under:\n\n~~~\nschedule-worker-locks/\n~~~\n\nThe lock is held for the lifetime of the worker object.\n\nOn POSIX systems v0.11 uses flock.\n\nOn Windows it uses msvcrt byte-range locking.\n\nThe operating system therefore releases ownership if the process dies.\n\nPersisted lease metadata is evidence and lifecycle context.\n\nThe live OS lock is the actual single-host mutual-exclusion fence.\n\n## Persisted worker leases\n\nReality Ledger adds:\n\n~~~\nschedule-worker-leases.jsonl\nschedule-worker-events.jsonl\nschedule-worker-ticks.jsonl\n~~~\n\nA ScheduleWorkerLease binds service identity, worker identity, generation,\nrenewal index, lease timestamps, bounded tick size, previous lease hash, and\nzero authority flags.\n\nA new owner after release increments generation.\n\nRenewal remains within the same generation and links to the previous lease hash.\n\n## Ownership events\n\nThe worker records ACQUIRED, ORPHAN_TAKEOVER, ACQUIRE_HELD, RENEWED, and RELEASED.\n\nORPHAN_TAKEOVER means the OS lock was available even though persisted history\nshowed a prior worker without a RELEASED event. That is the expected crash\nrecovery condition.\n\n## Lease expiry\n\nEvery tick and renewal verifies the persisted lease time boundary.\n\nAn expired lease cannot tick or renew. It must be replaced by a later worker\ngeneration.\n\n## Deterministic tick\n\ntick() performs one bounded worker cycle:\n\n~~~\nverify live OS lock\n→ verify lease unexpired\n→ reconstruct current v0.10 ScheduleService state\n→ derive next persisted cycle index\n→ build fresh cycle anchor\n→ choose bounded through_inclusive instant\n→ call ScheduleService.poll()\n→ persist ScheduleWorkerTickReceipt\n~~~\n\nThe worker does not maintain a trusted in-memory schedule cursor.\n\nThe persistent service state is reconstructed before every cycle.\n\n## Anti-drift cycle anchor\n\nEach tick computes a cycle anchor from service ID, worker ID, current lease hash,\npersisted cycle index, schedule-service state hash, and persistent cursor.\n\nEvery cycle receipt therefore pins itself to the exact state from which it\nstarted.\n\nThe cycle index is derived from persisted tick receipts rather than an in-memory\ncounter. Missing, duplicated, or non-contiguous indices fail closed.\n\n## Bounded time advance\n\nA worker tick may advance at most max_tick_seconds even when tick_at is much\nfarther ahead. Long downtime is processed through repeated bounded cycles.\n\n## NOOP cycles\n\nIf tick_at is not after the persistent cursor, v0.11 emits a NOOP tick receipt.\n\nThe service is not polled and the cursor does not change. The NOOP still consumes\na persisted cycle index so the worker history remains complete and observable.\n\n## Repetition acceptance\n\nv0.11 explicitly tests a 128-cycle chain and verifies:\n\n- cycle indices remain exactly 0..127;\n- every cycle anchor is distinct;\n- persistent cursor advances exactly one bounded step per cycle;\n- fresh reconstruction returns the exact final cursor;\n- the next persisted cycle index is 128.\n\nThis directly targets long-run automation drift.\n\n## Human / GUI interference boundary\n\nv0.11 does not perform GUI automation, so random popups, cursor movement, focus\nchanges, or desktop overlays cannot perturb schedule polling itself.\n\nFuture GUI adapters must not use blind coordinate replay as their primary\ncontract. They should require target window identity, semantic selectors when\navailable, foreground-state checks, unexpected-overlay detection, operator\nmouse/keyboard takeover detection, pre-action revalidation, post-action state\nverification, and HOLD rather than guessing.\n\nHuman desktop activity should be treated as possible operator takeover, not\nsomething automation fights.\n\n## Editable operator log boundary\n\nThe Reality Ledger remains immutable.\n\nAn editable human log should be a separate versioned annotation stream linked\nto immutable receipt or state hashes. Editing means appending a new revision and\nmaking it current, never rewriting the execution receipt it describes.\n\nThat companion contract is intentionally kept outside v0.11 worker ownership.\n\n## v0.11 acceptance gates\n\nWORKER-001: one live owner per service.\n\nWORKER-002: re-anchored due tick binds exact before/after state.\n\nWORKER-003: renewal preserves generation and links lease hashes.\n\nWORKER-004: expired lease cannot tick or renew.\n\nWORKER-005: later owner receives a new generation after release.\n\nWORKER-006: 128 consecutive cycles remain contiguous and reconstruct exactly.\n\nWORKER-007: tick at current cursor is an observable zero-authority NOOP.\n\n## Next rung\n\nThe next companion rung should add the versioned editable Operator Log and\nexplicit long-run / GUI interference guards before a user-facing macro recorder\nis allowed to drive mouse/keyboard interfaces.\n\nAfter that, the scheduler worker can be wrapped by a continuously running\nservice process without changing its ownership or tick semantics.\n
